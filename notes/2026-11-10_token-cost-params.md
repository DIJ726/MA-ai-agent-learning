# 学习笔记 · 周二 11/10 — Token、上下文窗口、Temperature / Top-P

> 学习目标：搞清楚调大模型时账单是怎么算的、为什么不能无限聊下去、temperature 到底调多大。

---

## 一、什么是 Token

Token 是大模型处理文本的**最小单位**，不是字，也不是词。

粗估经验（千问 tokenizer 大致符合，我们 `token_cost.py` 里就是这么算的）：

| 内容 | 大致 token 数 |
|------|--------------|
| 1 个汉字 | ≈ 1.5 token |
| 1 个英文单词 | ≈ 1.3 token |
| 1 个标点/空格 | ≈ 0.5 token |

实测（今天跑的）：
- 输入「北京明天天气怎么样，给我三句话建议」（15 个汉字）→ 真实 **17 token**（粗估 24，偏保守但量级对）
- 模型输出 210 token ≈ 150 个汉字左右

**关键认知**：你写的每一个字、prompt 里的每一个字、历史对话里的每一个字、模型回你的每一个字——**都算 token，都要钱**。

API 返回里的 `usage` 字段就是账单明细：
```json
"usage": {
  "prompt_tokens": 17,         // 输入（你+历史+system prompt）
  "completion_tokens": 210,     // 输出（模型回的）
  "total_tokens": 227           // 合计
}
```

## 二、上下文窗口（Context Window）

模型一次能"看到"的 token 上限，就是上下文窗口。超过就报错或被截断。

- qwen-plus：128K token（约 9 万汉字）
- 但**不是越大越好**——窗口越大，推理越慢、越贵
- 我们项目里 `MAX_HISTORY_TURNS = 20`：只保留最近 20 轮对话，老的自动丢掉，就是为了控制上下文长度

**为什么我们要截断历史**：
- 每多带一轮历史，下次调用就要多付一轮的输入 token 钱
- 上下文太长，模型注意力会分散（俗称"中间丢失"），回答质量反而下降
- 免费额度/套餐有 RPM（每分钟请求数）和 TPM（每分钟 token 数）限制，不控制会被限流

## 三、Temperature（温度）

控制模型输出的"随机性"。范围 0~2（千问默认 0.7）。

| 值 | 效果 | 适合场景 |
|----|------|---------|
| 0.0 | 几乎确定性，每次回答差不多 | 提取信息（"从问题里抠城市名"）、分类 |
| 0.3 | 轻微随机，稳定但不死板 | 结构化 JSON 输出（我们卡片用这个） |
| 0.7 | 默认值，自然流畅 | 日常对话、写建议 |
| 1.0+ | 很发散、有创意但可能胡说 | 写故事、头脑风暴 |

**我们项目里的用法**：
- `extract_cities_and_dates`：temperature=0.0（要它老实提取，不要发挥）
- `chat_json` 卡片：temperature=0.3（稳定但建议自然）
- 降级纯文本：temperature=0.7（让它像人一样说话）

## 四、Top-P（核采样）

另一个控制随机性的参数，范围 0~1。和 temperature 是"二选一调"的关系，一般不同时改。

- Top-P=0.1：只从概率最高的前 10% 候选词里选 → 保守
- Top-P=1.0：从所有候选词里选 → 完全放开

**经验法则**：
- 想"稳"：调 temperature
- 想"挑最可能的词"：调 top_p
- 一般**只调一个**，另一个保持默认，别两个都动

OpenAI 官方建议：不要同时改 temperature 和 top_p（我们项目里也没动 top_p，只用 temperature）。

## 五、成本意识（今天实测）

跑 `token_cost.py "北京明天天气怎么样，给我三句话建议"` 的真实账单：

```
输入 17 token × 0.0008 元/千 = 0.000014 元
输出 210 token × 0.002 元/千 = 0.000420 元
本次合计 ≈ 0.000434 元（不到半厘人民币）
```

外推：
- 每天 100 次这种问题 ≈ 0.043 元
- 一个月 ≈ 1.3 元

**所以**：
- 个人学习项目完全不用担心成本，qwen-plus 免费额度都用不完
- 真正烧钱的是：长上下文（每次带几万 token 历史）+ 长输出（每次让模型写 2000 字）+ 高频调用（每秒好几次）
- 优化方向：
  1. 及时截断历史（我们已经做了，`MAX_HISTORY_TURNS=20`）
  2. 能让模型输出 JSON 就别让它写散文（输出比输入贵 2.5 倍）
  3. 相同查询加缓存（我们的 `ttl_cache` 装饰器就是干这个的）
